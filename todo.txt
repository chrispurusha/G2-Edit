- Parameter Pages window — BUILT 2026-08-02 (src/paramPages.c / paramPages.h). The graphical
  stand-in for the G2 front panel's PARAMETER PAGES and their ASSIGNABLE KNOBS/BUTTONS (manual
  p.19 and p.89-91). Opened from Settings > Parameter Pages; NO keyboard shortcut, owner's
  explicit call 2026-08-02 (the original's Ctrl-F was implemented and then removed).
  Full-canvas panel per the owner's form decision: title bar with Slot A-D buttons and Close, a
  Patch/Global toggle, the 15 pages as a 3-wide x 5-high A1..E3 matrix, and the selected page's
  eight knobs in a row. Each cell shows position number, module name (Slot-prefixed on a Global
  page, since those can point into any Slot) and the live param widget.
  HOW IT'S PUT TOGETHER, since the shape matters more than the line count:
    * The knob widgets ARE the canvas's widgets — render_param_common() is called directly, so a
      dial looks like a dial, a toggle like a toggle, and every value string is formatted by that
      param type's own rule with no second implementation to keep in step. renderParams.c's ~30
      renderers hard-coded moduleArea (canvas zoom + scroll); they now take it from a file-scope
      area that set_param_render_area() (renderParams.h) switches to mainArea around the panel's
      render pass. A mode, not a parameter, to avoid threading an argument through 30 signatures
      and their function-pointer types.
    * Hit-testing reads back gParamRectangle, which render_param_common() has just written, so
      there is only one description of where a control is. Dragging fills in gParamDragging, i.e.
      the canvas's own drag machinery: cursor_pos() tracks it and sends the value. Mouse-up goes
      through the new finish_param_drag() (mouseHandle.h), extracted from the canvas's mouse-up so
      the undo push is shared — without it the panel's drags would be silently missing from Ctrl-Z.
    * Cross-Slot correctness: render_param_common(), the renderParams.c widgets, cursor_pos()'s
      drag branch and finish_param_drag() all now read module->key.slot rather than gSlot. A no-op
      on the canvas (which only ever draws the selected Slot) but required for a Global page, whose
      knobs can point at modules in any of the four Slots, each with its own active Variation.
    * The reverse direction was FREE, which answers the old open question: turning an assigned
      knob on the G2 arrives as an ordinary param change, usbComms.c's parse_param_change() writes
      it into the same module param, and the panel redraws from it. No new message handling. One
      change was needed: that function only woke GLFW for locationMorph, so it now also wakes
      whenever the panel is up.
    * Right-click a cell opens the canvas's own param context menu, so a knob can be reassigned or
      cleared from the page it's shown on.

  LAYOUT, reworked 2026-08-02 after the owner reported knob boxes overlapping each other. Two
  separate causes, both from the panel choosing rectangles that the canvas normally gets from
  paramLocationList:
   * NOTHING CLIPS - there is no scissor anywhere in SynthLib - and every widget paints
     left-anchored from the rect it is handed, growing rightwards by whatever its content needs.
     A fixed cell width therefore can't hold a wide value string or a wide strMap button, and the
     next cell's background then paints over the overflow. Cells are now measured
     (knob_metrics()) and the panel's width follows from the widest widget on the page, so
     switching pages can resize the panel.
   * paramTypeEnable is the exception to "the renderer sizes itself": render_paramType1Enable()
     draws a button exactly rectangle.size.w wide with the param's LABEL inside it. Handing it a
     fixed 26 is what put "Mod" in the button and "Amt" outside it on page A1 knob 6, whose param
     the patch has renamed "Mod Amt". The rect width is now per param type.
  Dials are centred on their cell (owner's request), and everything else has its painted block
  centred. That costs width: a centred dial draws its label and value from the dial's left edge
  rightwards, so the cell has to be about twice the content width. The sizing pass asks for that,
  and each cell falls back to block-centred and then to left-anchored if the window is too narrow
  to grant it.

  THE THREE SCOPES (this was the real subtlety — all three exist and they differ):
    CCompleteTreeIterator   (ctor 30321) — calls CTree::CIterator::base() first, so it walks UP to
                                           the chain root and covers the WHOLE tree. Used by CONNECT.
    CCompleteBranchIterator (ctor 30775) — no base() call, so it stays at the clicked connector and
                                           covers that BRANCH only. Used by COLOR and DELETE.
    partial / find_partial              — chain-ID-matched subtree, used inside BREAK.
  That is what reconciles the manual's two lines: "Cables in a serial cable chain will always have
  the same color" (connect repaints the whole tree) vs "Cables in a branch connection may have
  different colors" (COLOR only repaints one branch).

  WHAT EACH COMMAND DOES NOW:
   * DISCONNECT — splices the clicked connector out and rejoins the chain around it. One surviving
     neighbour becomes the new parent (the connector's own parent; the first child when the
     connector is the chain root, i.e. an output), and every other neighbour reattaches to it.
   * BREAK — unchanged in behaviour, refactored onto the shared layer. Still a no-op on a
     sourceless chain, still whitens the dead tail.
   * COLOR — now applies to the BRANCH (was: cables touching the clicked connector). Refused on a
     sourceless chain, because white is a state, not a user colour.
   * DELETE — new. Branch-scoped: the cable feeding the clicked connector plus its whole subtree.
     Matches "if you want to delete a complete branch connection, this must be done from the cable
     origin of the branch".
   * DELETE UNUSED CABLES — new. Patch-wide sweep. Computed from LIVE source-reachability rather
     than from the stored colour, since a patch loaded from a file or from a G2 written by an older
     build can carry a colour that predates the invariant, and this is not undoable.

- White cables — RULE IMPLEMENTED 2026-07-31, previously only understood. The invariant is:
      every cable in a chain shares ONE colour = the source output's signal-type colour,
      or WHITE (6) if the chain has no source output at all.
  MapConnectorColorToCableColor can never return 6; white only ever appears as the literal 6 on the
  no-chain-ID branches. That is what makes white unambiguously mean "this chain has no source".
  Colour is STORED and USER-OVERRIDABLE (the COLOR menu offers green and purple, which no signal
  type produces), so the recompute is conditional on SOURCE-REACHABILITY CHANGING, never
  unconditional — a blind recompute after every edit would destroy the user's colour choice.
  The minimal case that motivated all this now works: on a new patch, linking two mixer inputs to
  each other produces a WHITE cable immediately, because the new cable's chain has no source.
  Previously G2-Edit showed it red, a state the original cannot represent.
  Unit-tested headless (32 assertions over the shipped functions: white-on-sourceless, whole-tree
  repaint on connect, branch vs tree scope, Break's no-op and whitening at both an input and an
  output, Disconnect's splice at mid-chain and at the root, and the unused sweep). The harness is
  NOT in the repo — it lives in the session scratchpad and links cableChain.c / dataBase.c /
  moduleResourcesAccess.c with a stubbed msg_send. Worth reconstructing if this area is touched
  again; there is no test target in the Xcode project to host it.

  THREE CANDIDATE BEHAVIOURS (owner raised A and B; C is a suggestion):
   A. ASK WHICH WINS — "keep the synth's patch" vs "push the editor's patch to the synth". Best
      ergonomics, but the second branch is a destructive write to the synth's edit buffer, so it
      needs the same care as the Bank Restore work.
   B. OFFER TO SAVE FIRST — save the editor's patch to a file, then load the synth's. Strictly

      someone has plugged in a cable, and nothing is ever lost. Cheapest to build once dirty
      tracking exists, and it degrades gracefully: if the divergence did not matter, the user
      ignores the message.

  WHAT SHIPPED (owner chose A + C: auto-preserve, then ask):
   * DIRTY TRACKING TURNED OUT TO BE FREE. While online every edit is sent to the G2 as it is made,
     so the copies can only drift while it is away — and those edits are already recorded in the
     USB command queue, which state_handler() only drains when online. Anything sitting in it at
     reconnect was enqueued while the G2 was gone, and each message carries its slot. So the drain

     reconnect is about to replace; replaying them would edit whatever now occupies each index.

     also what the owner asked for.
   * THE PULL IS DEFERRED, not done-then-regretted: new eCommsAwaitingSyncDecision state parks the
     USB thread until the user answers. That deferral is the actual bug fix.
   * RECOVERY FILE FIRST, then the dialog: one .pch2 per dirty slot in
     ~/Library/Application Support/G2-Edit/Recovery, so no answer — including Escape — can lose
     the work, and the dialog says so. Pruned to the newest 10 on each write, and deleted only on
     a successful "Save As..." (never on the Pull branch, where it is the only copy left).
   * Three-way dialog: Send to Synth / Save As... / Pull from Synth. Escape means Pull. Undo is
     cleared on every branch, because after a wholesale push or replacement its entries describe a
     device state that no longer exists.
   * Needed a 3-button alert (SynthLib show_choice) — see the SynthLib entry under AWAITING OWNER

ARCHITECTURE — RATIONALISE AND COMMONALISE FOR THE OTHER PROJECTS

***PRIORITY*** (identified 2026-07-25 by diffing G2-Edit / EmuUtility / SynthEdit directly — concrete,
mostly-mechanical dedup + decoupling wins at the host<->SynthLib boundary; do these before the bigger
open design items below):

1. [PRIORITY] Shared graphics/window bootstrap. init_graphics() and every window callback
   (framebuffer_size_callback / content_scale_callback / window_size / window_pos / window_close) are
   ~90% character-identical across all three apps: same glfwWindowHints, same glfwCreateWindow, same
   context/FreeType/scale init, same callback wiring. Only real differences: dial-mode default,
   topBarHeight, whether wake-callbacks are registered, and the callback function *names* (key_callback
   vs key_cb — a non-issue, they go in a struct). There is already a precedent seam (apps pass
   configure_synthlib_theme((tSynthLibTheme){...}) — utilsGraphics.h). Extend it:
       tGlfwWindow * synthlib_window_create(const tSynthLibWindowConfig * cfg,  // title, size, topBarHeight, dialModeDefault
                                            const tSynthLibCallbacks   * cbs);  // key/char/cursor/button/scroll/resize fn-ptrs
   Effort low, risk low, removes ~150 lines x2.

2. [PRIORITY] Popup lifecycle coordinator — the cleanest DECOUPLING win. SynthLib owns the popup
   WIDGETS (file/bank/alert browsers, context menu, menu bar) but NOT their orchestration, so each host
   re-implements it four separate times: (a) render order (every app calls render_context_menu ->
   render_file_browser -> render_bank_browser -> render_alert_dialog back-to-front, with the same
   "drawn last - modal" comment copy-pasted verbatim); (b) modal-priority CLICK dispatch cascade
   (if file_browser_active(){...return;} if bank_browser_active(){...} if alert_dialog_active(){...} —
   14 routing refs each in G2-Edit and SynthEdit mouseHandle.c); (c) the same cascade again for
   KEY/CHAR; (d) per-frame hover tick (update_context_menu_hover / update_menu_bar_hover /
   update_bank_browser_hover — the host must remember to call each every frame). That last one has
   ALREADY shipped real bugs: SynthEdit's own comments document "never actually called anywhere until
   now" hover reports (2026-07-11, 2026-07-24). An order-dependent contract spread across the host is
   fragile by construction. Fix = a coordinator façade that internalises the z-order (SynthLib
   registered the popups, so it knows the stacking):
       bool synthlib_popups_dispatch_click(tCoord coord, eClickPhase phase); // true if a modal consumed it
       bool synthlib_popups_dispatch_key(int key, int action);
       void synthlib_popups_tick(void);    // replaces all the update_*_hover() calls
       void synthlib_popups_render(void);  // one call, correct back-to-front order
   Each host's mouse_button / key / loop / render_frame collapses to a single guarded call. Turns a
   ~20-symbol order-sensitive surface into 4 functions. Effort medium, risk low-medium (mechanical but
   touches the hot input path in all three apps — sequence carefully). DO THIS FIRST of the priority set.

3. [PRIORITY] Move mouse-callback plumbing into SynthLib (ties into 1 & 2). The common preamble in
   every app's mouse handling is boilerplate over SynthLib-owned state:
     - get_global_gui_scaled_mouse_coord() (window pixels -> logical/GUI-scaled coords) is DUPLICATED
       per-app: EmuUtility's and SynthEdit's are character-identical (both delegate to
       window_to_logical()), G2-Edit's is functionally equivalent but inlined. Pure math over
       gGlobalGuiScale + get_render_width/height, all already in SynthLib -> clean move
       (synthlib_window_to_logical() / synthlib_mouse_coord()).
     - convert_to_mouse_button() (GLFW button/action -> normalized button+phase) is generic decode.
     - The thin GLFW callback adapter itself (decode -> scale coord -> popup-coordinator dispatch (2)
       -> app handler(coord, button) -> request_redraw) can be shared, unifying the two conventions
       that exist today (EmuUtility/SynthEdit's *_cb -> handle_* split vs G2-Edit's
       callbacks-are-handlers directly). App keeps only its domain hit-testing. NOTE: the app-specific
       hit-testing cannot fully move until the gParamRectangle -> click-region migration below
       decouples hit-testing from render-time global arrays; after that, even more of the dispatch
       could move. Do the coord-transform + normalized-callback-adapter part now (independent of that),
       leave domain hit-testing local.

4. [PRIORITY] CoreMIDI send-primitive extraction (safe first step of the comms-layer item below).
   EmuUtility and SynthEdit's low-level MIDI send is near-identical (MIDIPacketListInit /
   MIDIPacketListAdd / MIDISend over the same gMidiOutPort/gMidiDest globals; SynthEdit just has a
   bigger sysex buffer). Move the packet-send primitive + the CoreMIDI handle globals

DO NOT RE-TRY (conclusions from completed work — the reasoning is gone from this file, the constraint is not)

- FT_LOAD_FORCE_AUTOHINT in the glyph rasteriser: tried and REJECTED. Crisper, but it changes glyph
  advances, and with canonical-advance positioning it renders "R andomA 1" / "554.4H z". Do not re-try
  without also making get_text_width() use the same hinted advances — which it cannot, as it never sees
  the device size (gZoomFactor). FT_LOAD_TARGET_LIGHT is the deliberate choice: snaps stems vertically
  while leaving horizontal metrics linear.
- Text layout is deliberately NOT driven by the per-size atlases. get_text_width() and everything built
  on it stay on ONE canonical metrics set (gCanonInfo, measured once at GLYPH_REFERENCE_PX) so widths
  stay continuous and boxes fit. The pen advances by the canonical advance; only each glyph's final
  position is rounded. That costs sub-pixel letter spacing and buys pixel alignment — the right trade
  at 6px.
- gMaxAscent/gMaxDescent must stay canonical, and the baseline must be derived from that canonical
  ascent (round(coord.y + gMaxAscent * scaleFactor), rounded ONCE). An earlier version used each
  atlas's OWN rounded ascent, which rounds a second time against a rasterization whose em height only
  approximates the requested one — that is what caused the intermittent "text renders slightly low"
  drop, since the ascent-to-em ratio is not constant across rasterization sizes.
- Rasterizing 1:1 was tried as a fix for small-text mush and made it WORSE. The root cause was the draw
  path resampling every glyph at an arbitrary sub-pixel phase, not the atlas size.
- The 640x360 minimum window size limits INTERACTIVE resizing only, and that is accepted (owner call:
  do not over-complicate). On macOS, Cocoa applies setContentMinSize:/setContentAspectRatio: to user
  drags but not to programmatic setFrame:, so glfwSetWindowSize() bypasses it and a windowWidth pref
  saved below 640 is restored at its saved size. Self-heals as soon as the window is resized by hand.
- EmuUtility's TARGET_FRAME_BUFF_HEIGHT was changed to 1440 (from 1200) to match the other two at 16:9.
  Safe because nothing lays out against that constant — it only drives window creation size, the size
  limit, the aspect lock and the saved-height derivation, while UI scale comes from
  synthlib_scale_init(TARGET_FRAME_BUFF_WIDTH), i.e. WIDTH only. EmuUtility's content is all
  top-anchored, so 16:9 just leaves more empty grey below it.
- The Seq park LED's exclusion from the LED stream is CORRECT and must STAY — it is what keeps the
  module's other real stream LEDs aligned. (See the open Seq park-LED item above for what is still
  unknown.)
- render_volume_meter stays G2-local in moduleGraphics.cpp. Moving it to SynthLib alongside
  utilsGraphics.cpp was considered and DROPPED: it is pure G2 domain (tVolumeType /
  tVolumeMeterConfig / volumeMeterStyle* enum + G2 value-bit decode) built entirely on primitives that
  are ALREADY shared. Moving it would couple SynthLib to G2 module semantics — the opposite of the
  commonalise goal.
- mouseHandle.c:1585 — mouse-move calls synthlib_request_redraw() unconditionally on every move. A
  "only redraw if hover state actually changed" guard (noAction) used to exist and was disabled,
  commented out rather than deleted. Re-adding it risks reintroducing whatever bug caused it to be
  pulled (no record of why) for a performance win that is likely marginal on modern hardware. Leave
  alone unless it is actually observed as a real cost.
- The reverse-queue design deliberately keeps coalescing dirty-bits as flags, not messages
  (gotPatchChangeIndication[], gotPerfSettingsChangeIndication, gReDraw, EmuUtility's gNeedLcdFull/
  gNeedLcdDelta/gLcd.refresh/gLeds, SynthEdit's gRescanNeeded/gReconnectRequested, and
  gStateDumpDebounceTicks which is a debounce counter). gRescanNeeded is additionally a wait-break
  condition inside the connect loops' 100ms slices — a flag's job, not a message's.
- EmuUtility's and SynthEdit's MIDI threads poll-drain with eRcvPoll and do NOT block on eRcvWait like
  G2-Edit's USB thread. They are CFRunLoop-driven (CoreMIDI's notify callback is tied to that run loop)
  and have their own time-based cadences; blocking in msg_receive would stall both. Neither app has a
  gToGuiThread (MIDI->UI) — everything they report upward today is a coalescing dirty-bit, so an empty
  reverse queue would be speculative.
- gLcd uses a mutex, not a double-buffer, because deltas mutate the accumulated frame in place so there
  is no clean front/back to swap. The lock is never held over a GL call.
- eMsgCmdScanDevices is COALESCED in EmuUtility's drain (a local bool; the scan runs once after the
  batch) because a rescan is a wanted-state, not an event: one hub plug can fire several
  kMIDIMsgSetupChanged notifications and each scan walks every destination at 15ms stagger.
- module->connector[i].type deliberately stores only the raw base type, never the upRate promotion —
  protocol.c's own upRate-propagation walk depends on it being the permanent declared type. Use
  effective_connector_type(baseType, upRate) at the point of use instead.
- menus.c is NOT a commonalise candidate. The underlying mechanism (tMenuItem, open_context_menu,
  contextMenu.c) is already fully shared via SynthLib. G2-Edit's menus.c is still 2125 lines
  (EmuUtility/SynthEdit's are 26/95), but what remains is legitimately G2-specific domain action logic
  operating on tModule/tParam/tCable, which do not exist in the other two apps.
