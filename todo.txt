  clear_slot_data() (graphics.cpp), called from both the USB (usbComms.c:2920) and file-load (graphics.cpp:700)

- msgQueue.h "remove unused mutex" — was wrong; re-checked msgQueue.c and BOTH mutex and semMutex are genuinely
  used (mutex guards head/tail, semMutex+semCond+semCount implement the counting semaphore). The "TODO - use
  this" comment on semMutex was just stale from before semMutex was wired up. Comments updated to explain what
  each one actually guards instead.
- moduleGraphics.cpp:849 upRate connector-colour bug — FIXED, full fidelity. First pass confirmed against
  the manual (g2manual.txt p.135) only; second pass cross-checked the actual decompiled original editor
  (Original Editor/G2Editor.c) and found the real mechanism: ECableColor has 7 values including a genuine
  TurboLogic entry (RGB 0xff/0xc0/0x50 ≈ 1.0/0.75/0.31, i.e. orange), and CPnlControlInHole/OutHole::GetColor()
  / CPnlLogicInHole/OutHole::GetColor() both branch on EModuleBandWidth — confirming Control connectors
  promote to Audio and Logic connectors promote to their OWN higher-bandwidth variant (TurboLogic/orange),
  never to plain Audio. Added connectorTypeTurboLogic to tConnectorType (types.h) and its RGB to
  connectorColourMap (moduleResources.h); added a shared effective_connector_type(baseType, upRate) helper
  (moduleResourcesAccess.c/.h) used by both the connector-hole rendering (moduleGraphics.cpp) and, for full
  fidelity, cable-creation's "inherit the source connector's current colour" logic (mouseHandle.c:712, which
  previously used the connector's raw base type and so never inherited the promoted colour either).
  gCableColourMap already had an unused cableColourOrange entry ("Logic FG") ready for exactly this — wired
  cable_colour_for_connector_type() to it. module->connector[i].type itself deliberately still stores only
  the raw base type, never the promotion — protocol.c's own upRate-propagation walk (search
  "fromModule->connector" there) depends on it being the permanent declared type.
- update_module_up_rates() (protocol.c) — checked against the decompiled original's real equivalent,
  CPatchData::GenerateBandwidthChangeMolecules() (same do-while-until-stable fixed-point shape, same
  "reset then recompute" pattern so demotion works, not just promotion). Structurally sound — but the
  comparison surfaced a real gap: the original also walks a just-changed module's OUTPUT connectors and
  retroactively recolours any already-connected cable (GetRecolorCableMolecules) the moment the module's
  bandwidth changes; this app only ever set a cable's colour once, at creation time (mouseHandle.c), so an
  existing cable's colour went stale if its source module up-rated or de-rated afterwards. FIXED: added the
  same retroactive-recolour walk to update_module_up_rates()'s per-module change branch, reusing the exact
  cable-matching shape menu_action_set_cable_colour() (menus.c) already uses for the user-driven manual
  recolour, and sending the same eMsgCmdWriteCable sync every other cable-colour change already sends.
- protocol.c:355 numVariations sanity check — added: logs an error if the parsed value is neither 9 nor 10
  (this function has no way to know if it's parsing USB or file data, so it can't check the exact expected
  value for the actual source, just flag anything outside the known pair). The existing >10 bounds check
  that prevents an actual overrun was already there and is unchanged.

MISSING FEATURES (parity with the original editor — cross-checked against g2manual.txt 2026-07-25;
none of these exist in G2-Edit at all yet, confirmed by source search, not just absence of memory):
- Pop-up overlay views (F5-F8, Ctrl+F8 in the original) — a family of "yellow popup box" overlays drawn
  over the patch canvas showing a different thing per parameter at a glance, toggled by function key:
    F5        View Parameter Values     — each parameter's current value
    F6        View Morph Groups         — which of the 8 morph groups (if any) each parameter belongs to
    F7        View Knob Assignments     — which panel knob (if any) each parameter is mapped to
    F8        View MIDI CC# Assignments — the MIDI CC# (if any) mapped to each parameter
    Ctrl+F8   View Parameter MIDI Values — how each knob is actually being sent/received over MIDI
  None implemented — no F5-F8 key handling anywhere in the source at all.
- Parameter Overview window (Ctrl-L) — floating window showing every Parameter Page's knob/button
  assignments at once in one grid, with drag-and-drop to make/move/reorganize assignments directly from
  the overview instead of one page at a time. Not implemented.
- Bulk MIDI CC tools (Tools menu, alongside Parameter Overview) — "Assign MIDI" (auto-assigns the next
  free CC# to every currently panel-assigned knob/button, in page order), "Clear MIDI" (clears every CC#
  assignment in the Patch at once, reversible via Undo), "View Buttons" (toggles the popup overlay between
  a combined dial+button assignment's knob half and button half, e.g. on Sequencer modules). None
  implemented — G2-Edit's Tools menu currently only has Mutator. Per-parameter right-click "Assign MIDI
  CC" already exists (the "M key / MIDI CC# Assign Dialog" equivalent) and doesn't need redoing.
- MIDI Learn (L key) — assign the currently-focused parameter to whichever MIDI CC# was last received,
  without opening a picker. Not implemented.
- Patch Window Split Bar — the original shows the Voice Area and FX Area SIMULTANEOUSLY in one window,
  split by a drag-resizable horizontal bar (with up/down-arrow buttons to show just one area full-height,
  a double-arrow button to restore the previous split position, and V/F keyboard shortcuts to toggle full-
  screen on the current area and back). G2-Edit's VA/FX topbar buttons (mouseTopbar.c,
  set_exclusive_button_highlight(topbarVaId, topbarFxId, ...)) are a hard exclusive toggle instead — only
  one of VA/FX ever visible, no split view, no drag bar, no V/F shortcuts, no "restore previous split"
  concept at all.
- Virtual/On-Screen Keyboard (Ctrl-K) — floating window to play notes with the mouse without a physical
  synth keyboard attached: click-to-sound keys (sustains while held), horizontal resize to widen the

  note replays continuously) toggles. Not implemented — zero references anywhere in the source.
- Cable BREAK action — right-click cable popup currently only has Disconnect (menu_action_delete_cable,
  menus.c — fully removes one cable, auto-rerouting any remaining serial chain to stay functional). The
  original ALSO has Break: splits a serial chain at one point WITHOUT rerouting — everything before the
  break point keeps working, everything after becomes "connected but non-functional" and turns white to
  show it's dead wire (this is what the existing "delete non-functional input-to-input connections (white
  cables)" cleanup comment elsewhere in menus.c was referring to — G2-Edit already has the CONCEPT of
  these white cables, just no UI action that actually creates them). Not implemented.

  - Shared host injection point (tSynthLibHost, synthlibHost.h/.c) — replaced the old convention of every

  - gWindow/gQuitAll/gReDraw/gDialMode + tDialMode — moved into SynthLib (synthlibGlobals.h/.c,

    its own extra settings (zoom, last-browsed folder, device config) local.

  PARTIALLY DONE / STILL OPEN:
  - Migrate G2-Edit's gParamRectangle[slot][location][index][param] onto the click-region registry —
    NOT finished. It's a 6MB static array (globalVars.c's own comment says so) still doing double duty:
    feeds register_click_region() at render time (moduleGraphics.cpp) AND is read directly via
    within_rectangle() in a few mouseHandle.c spots (~258, 458, 1078) that look like they may predate the
    click-region migration — worth checking whether those are dead code now shadowed by
    dispatch_click_region(), or still load-bearing (e.g. mid-drag angle calculation genuinely needs the
    rect, not just a hit test). Other named hit rects (gPatchParamClose, gTopbarControls[].rectangle) are
    still direct array indexing too.
  - Generalize mousePanels.c/mouseTopbar.c/selection.c into shared SynthLib components — blocked on the
    above: hit-testing needs to be fully decoupled from render-time global arrays first, same ordering
    the original note had.
  - Page-selection tabs — SynthEdit built its own render_page_tabs()/page-tab mechanism independently
    rather than as a generalization of G2-Edit's topbarControls.def X-macro + set_exclusive_button_
    highlight() pattern. Both now exist, unrelated to each other. Unifying them into one SynthLib "page
    tab row" component (with pages as a grouping construct in a shared descriptor schema) is still open —
    arguably easier now that there are two concrete implementations to compare instead of one plus a
    proposal.
  - Design one shared descriptor schema (control type, rect+anchor, range/default, string-map ref,
    colour-map ref) reusable as both a compile-time C table (G2-Edit) and a runtime-parsed file
    (SynthEdit) — still just an idea, no prototype. Bigger lift than anything else on this list: G2-Edit's
    module system (200+ types, dynamic instantiation, morphing) and SynthEdit's flat per-device panel are
    genuinely different shapes, not just different loaders for the same shape.
  - Anchor-based layout resolver (adjust_rectangle equivalent) alongside the hit-registry — still open,
    depends on the descriptor-schema work above.
  - Evaluate generalizing the msgQueue.c + usbComms.c thread/message-queue pattern into SynthLib as a
    transport-agnostic comms layer (USB vs MIDI as pluggable backends) — still open, and the highest-value
    remaining item on this list: EmuUtility/SynthEdit talk to CoreMIDI directly with no queue abstraction
    at all (UI thread and MIDI thread share state via plain globals + a wake callback), where G2-Edit
    already has the safer enqueue/dequeue pattern for USB. A smaller, currently-scoped first step: just the
    CoreMIDI globals (gMidiClient/gMidiInPort/gMidiOutPort/gMidiSource/gMidiDest), the wake-callback
    boilerplate, and the low-level MIDIPacketList send primitive are identical between EmuUtility and
    SynthEdit (G2-Edit uses USB, not MIDI, so it's a 2-of-3 candidate) and could move to SynthLib on their
    own without touching either app's actual scan/connect/dispatch logic, which has diverged for good
    reason (SynthEdit's is a much more developed generic multi-device framework — deferred identity-reply
    buffering, three destination-matching fallback strategies, per-source running-status parsing for
    shared MIDI interfaces — vs EmuUtility's simpler single-device E-mu client) and isn't safe to merge
    mechanically.
