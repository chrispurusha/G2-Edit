- PANEL perf<->patch toggle (both directions): device sends an unsolicited SUB_RESPONSE_PERF_PATCH_VERSIONS
  (0x1f); the editor handles it via its existing "Perf settings change — reloading all slots" path. The
  editor UI followed the panel correctly both ways (verified on screen). No 0x11 perf-header, no 0x3e.

  replies with 0x1f (+0x29). The device never sends 0x3e back. So parse_perf_mode_change() — dispatched
  ONLY from an incoming 0x3e — is never reached on any path (editor toggle, panel toggle, or perf load).
  "Got perf mode change" never logged. => effectively dead; safe-to-remove candidate (like parse_perf_header).
- PerfMode ownership (:360): parse_synth_settings() DOES write gGlobalSettings.perfMode, and it read STALE

  the synth-settings copy lags — treat the 0x1f/perf path as authoritative, not synth settings.
- SUB_RESPONSE_PERF_HEADER (0x11) / parse_perf_header: never sent on ANY path tested (file load, panel
  toggle, editor toggle). Strongly supports defs.h:179's "might want to remove".
- Voice count / assigned voices (:594): the editor only ever GETs assigned voices (send_get_assigned_voices,

PERF-MODE HARDWARE FINDINGS (2026-07-26 — captured on real G2 via ENABLE_USB_LOG + Debug LOG_DEBUG;
experiment: load an empty .prf2 from a starting state of Patch Mode + Online. Raw capture archived in the
session scratchpad as perfload_capture.log):

  What actually happens when load_file_into_database() loads a perf while perfMode==0 (graphics.cpp:711):
    1. UI thread enqueues eMsgCmdWriteModePerf, then usleep(2s), then clear_slot_data() x4 + parse_perf()
       (populating the in-memory database with the NEW perf), then enqueues eMsgCmdWritePerf.
    2. USB thread dequeues eMsgCmdWriteModePerf -> send_perf_mode_change(1) (round-trips, gets
       SUB_RESPONSE_PERF_PATCH_VERSIONS 0x1f) + send_get_performance_settings() (gets 0x29).
    3. The mode switch makes the G2 asynchronously raise patch-change indications for ALL FOUR slots.
       state_handler() services these at the TOP of its loop (before the next msg_receive), calling
       send_get_patch_data() per slot — a full 4-slot read cascade that writes the device's OLD patches
       into the SAME in-memory database. In the capture this cascade ran ~40.78-41.05s.
    4. ~2s after step 1, the UI thread's sleep ends; its clear+parse (which overwrites the database with the
       NEW perf) therefore runs AFTER the cascade, then eMsgCmdWritePerf is dequeued and the 4 CMD_SET_PATCH
       (0x37) writes go out (~41.94s). No patch re-reads happen after the write (verified: only 0x29/0x11-
       keysplit/master-clock writes follow) — so nothing clobbers the write afterwards.

  => The sleep is LOAD-BEARING, and its real job is NOT "wait for perf mode to be stable" — it's to ensure
     the device's async patch-change-indication cascade (step 3) is fully serviced BEFORE the UI thread does
     clear_slot_data()+parse_perf() (step 4). Without it, the cascade's send_get_patch_data() reads would
     overwrite the freshly-parsed perf in the shared database before eMsgCmdWritePerf sends it, and the load
     would write the device's OLD patches straight back. It's a genuine UI-thread-vs-USB-thread database race,
     papered over with a fixed delay.
  => Confirmed the load is CORRECT with the sleep: after loading the empty perf, all 4 slots (A-D) showed
     empty/"No name", i.e. the device's previous perf (BCHydro_DZ / Control_DZ / Drums_DZ / Synth_DZ /
     Extra_DZ) was fully replaced, no clobber. (The OLD names DO appear transiently in the debug log — those
     are step 3's cascade reading pre-write state, later wiped by step 4's clear+parse.)
  => Proper fix direction: eliminate the cross-thread race rather than time it. Cleanest is to move the whole
     load (clear+parse+write) onto the USB thread as a single ordered message so it can't interleave with
     indication servicing; alternatively a handshake where the UI thread waits until the USB thread signals
     "perf mode confirmed AND no patch-change indication seen for N ms". Either removes the blind 2s.

  Bonus data point for the SUB_RESPONSE_PERF_HEADER (0x11) question (defs.h:179 / usbComms.c:600,925):
  across the entire perf-switch capture the device NEVER sent a 0x11 header response — it used
  SUB_RESPONSE_PERFORMANCE_SETTINGS (0x29), exactly as the code comment suspected. parse_perf_header() went
  uncalled. Not yet proof it's dead on ALL paths (panel-initiated perf-mode toggle not yet captured), but it
  is confirmed unused on the file-load perf-switch path.

- rationalise architecture and commonalise components for other projects (status as of 2026-07-25)

  ***PRIORITY*** (identified 2026-07-25 by diffing G2-Edit / EmuUtility / SynthEdit directly — these
  are concrete, mostly-mechanical dedup + decoupling wins at the host<->SynthLib boundary, do these
  before the bigger open design items below):

  1. [PRIORITY] Shared graphics/window bootstrap. init_graphics() and every window callback
     (framebuffer_size_callback / content_scale_callback / window_size / window_pos / window_close)
     are ~90% character-identical across all three apps: same glfwWindowHints, same
     glfwCreateWindow(TARGET_FRAME_BUFF_WIDTH/4, ...), same context/FreeType/scale init, same callback
     wiring. Only real differences: dial-mode default, topBarHeight, whether wake-callbacks are
     registered, and the callback function *names* (key_callback vs key_cb — a non-issue, they go in a
     struct). There's already a precedent seam (apps pass configure_synthlib_theme((tSynthLibTheme){...})
     — utilsGraphics.h). Extend it:
         tGlfwWindow * synthlib_window_create(const tSynthLibWindowConfig * cfg,   // title, size, topBarHeight, dialModeDefault
                                              const tSynthLibCallbacks   * cbs);   // key/char/cursor/button/scroll/resize fn-ptrs
     Effort low, risk low, removes ~150 lines x2.

  2. [PRIORITY] Popup lifecycle coordinator — the cleanest DECOUPLING win. SynthLib owns the popup
     WIDGETS (file/bank/alert browsers, context menu, menu bar) but NOT their orchestration, so each
     host re-implements it four separate times: (a) render order (every app calls render_context_menu ->
     render_file_browser -> render_bank_browser -> render_alert_dialog back-to-front, with the same
     "drawn last - modal" comment copy-pasted verbatim); (b) modal-priority CLICK dispatch cascade
     (if file_browser_active(){...return;} if bank_browser_active(){...} if alert_dialog_active(){...} —
     14 routing refs each in G2-Edit and SynthEdit mouseHandle.c); (c) the same cascade again for
     KEY/CHAR; (d) per-frame hover tick (update_context_menu_hover / update_menu_bar_hover /
     update_bank_browser_hover — host must remember to call each every frame). That last one has ALREADY
     shipped real bugs: SynthEdit's own comments document "never actually called anywhere until now"
     hover reports (2026-07-11, 2026-07-24). An order-dependent contract spread across the host is
     fragile by construction. Fix = a coordinator façade that internalises the z-order (SynthLib
     registered the popups, so it knows the stacking):
         bool synthlib_popups_dispatch_click(tCoord coord, eClickPhase phase); // true if a modal consumed it
         bool synthlib_popups_dispatch_key(int key, int action);
         void synthlib_popups_tick(void);     // replaces all the update_*_hover() calls
         void synthlib_popups_render(void);    // one call, correct back-to-front order
     Each host's mouse_button / key / loop / render_frame collapses to a single guarded call. Turns a
     ~20-symbol order-sensitive surface into 4 functions. Effort medium, risk low-medium (mechanical but
     touches the hot input path in all three apps — sequence carefully). DO THIS FIRST of the priority set.

  3. [PRIORITY] Move mouse-callback plumbing into SynthLib (ties into 1 & 2). The common preamble in
     every app's mouse handling is boilerplate over SynthLib-owned state:
       - get_global_gui_scaled_mouse_coord() (window pixels -> logical/GUI-scaled coords) is DUPLICATED
         per-app: EmuUtility's and SynthEdit's are character-identical (both delegate to
         window_to_logical()), G2-Edit's is functionally equivalent but inlined. It's pure math over
         gGlobalGuiScale + get_render_width/height, all already in SynthLib -> clean move
         (synthlib_window_to_logical() / synthlib_mouse_coord()).
       - convert_to_mouse_button() (GLFW button/action -> normalized button+phase) is generic decode.
       - The thin GLFW callback adapter itself (decode -> scale coord -> popup-coordinator dispatch (2) ->
         app handler(coord, button) -> request_redraw) can be shared, unifying the two conventions that
         exist today (EmuUtility/SynthEdit's *_cb -> handle_* split vs G2-Edit's callbacks-are-handlers
         directly). App keeps only its domain hit-testing (modules/cables/dials for G2, panels for the
         others). NOTE: the app-specific hit-testing can't fully move until the gParamRectangle ->
         click-region migration below decouples hit-testing from render-time global arrays; after that,
         even more of the dispatch could move. Do the coord-transform + normalized-callback-adapter part
         now (independent of that), leave domain hit-testing local for now.

  4. [PRIORITY] CoreMIDI send-primitive extraction (safe first step of the comms-layer item below).
     EmuUtility and SynthEdit's low-level MIDI send is near-identical (MIDIPacketListInit /
     MIDIPacketListAdd / MIDISend over the same gMidiOutPort/gMidiDest globals; SynthEdit just has a
     bigger sysex buffer). Move the packet-send primitive + the CoreMIDI handle globals
     (gMidiClient/gMidiInPort/gMidiOutPort/gMidiSource/gMidiDest) into SynthLib WITHOUT touching each
     app's scan/connect/dispatch logic (which has diverged for good reason — see the comms bullet in
     "PARTIALLY DONE" below). 2-of-3 (G2-Edit is USB, not MIDI). Small, safe, unblocks the bigger queue
     abstraction. Render-loop skeleton extraction (synthlib_run_frame_loop) is possible but LOW priority
     — do it last, after 1-3, since the per-frame "flush hooks" are genuinely app-specific.
