- SUPER-SAW ("sup") PHASE FIX NEEDS AN EAR (2026-08-09). Fixed as part of the warnings sweep, because
  the compiler had been pointing at it for months: gSuperPhase is [MAX_VOICES][MAX_ENGINE_NODES][2] and
  osc_waveform() indexed it gSuperPhase[node][0], putting the NODE number in the VOICE position. Passing
  a `double (*)[2]` where a `double *` was expected is exactly what a two-deep index into a three-deep
  array produces, which is what -Wincompatible-pointer-types was saying. osc_waveform() now takes
  `voice` and indexes [voice][node][0..1].
  NOT out of bounds before the fix, by luck: 28 nodes fits inside 32 voices.
  WHAT IT AFFECTS: "sup" is the fifth entry in OscB's Wave menu (sin/tri/saw/squ/sup,
  moduleResources.h:450) and our engine approximates it as three saws at 0, +10 and -10 cents — see the
  KNOWN GAPS list at the top of soundEngine.h. The two detuned saws are the only things in the engine
  needing phase state beyond the main oscillator's, which is why this was the only place with the bug.
  Only oscillator nodes reach it; LFOs take a different path and never touch gSuperPhase.
  HOW TO CHECK: OscB with Wave = sup, then play a CHORD. Before the fix every voice in that chord shared
  one pair of detune phases, so the voices were phase-locked to each other; each should now have its own
  and the chord should sound thick rather than flat. Two OscB modules both on sup is the other case —
  they used to tread on each other's storage. A single voice with one sup oscillator is unchanged by
  construction (it read [node][0][0] and now reads [0][node][0] — same value, different slot), so if the
  single note sounds different, something else is wrong.

- File > Save CRASH — FIXED 2026-08-04, needs the owner to confirm it stops recurring. Owner
  reported an occasional crash on a straight Save (never on Save As), stack ending in
  remember_file_path() -> COPY_STRING. TWO DEFECTS, both in the same two lines:
   1. SELF-COPY, which is undefined behaviour, not a harmless no-op. eRspSaveToCurrentPath
      (graphics.c) takes its path FROM gSavedPatchPath[gSlot] and hands it to on_file_saved(),
      which finally remembers it back INTO that same buffer — so strncpy(dst, dst, n). strncpy's
      parameters are restrict-qualified, so the compiler may assume the regions do not overlap and
      vectorise on that basis. Save As never hit it because the file panel supplies a fresh buffer.
      COPY_STRING now guards dst != src, which protects every call site rather than just this one.
   2. COPY_STRING EXPANDS ITS DESTINATION THREE TIMES (the strncpy, the sizeof, and the terminator
      write), and gSlot is _Atomic — so COPY_STRING(gSavedPatchPath[gSlot], ...) was three separate
      atomic loads. A slot change part way through would terminate a DIFFERENT slot's buffer than
      the copy went into. Silent corruption rather than a crash. remember_file_path() now reads the
      slot once into a plain local and bounds-checks it. The macro carries a note that its
      destination must be a side-effect-free array expression.
  VERIFICATION IS WEAK ON PURPOSE-OF-RECORD: ten consecutive saves back to the same path did not
  crash, but the fault was intermittent and undefined behaviour frequently appears to work. The
  argument is that the UB is gone, NOT that its absence was reproduced. If it ever recurs, the fact
  that it is no longer a self-copy narrows the search a lot.
  STILL OPEN, deliberately not fixed here: the slot can still change between the call site reading
  gSlot to build the path and remember_file_path() reading it again — the call site already carries
  a comment acknowledging that race. It is a correctness wrinkle, not a crash; fixing it properly
  means threading the slot through as a parameter rather than re-reading the global.

- Sound engine FltClassic — moved closer to the hardware 2026-08-05, measured against the manual
  rather than by ear. Two changes, both removing something the engine was doing that the G2 is not:
   * NO PASSBAND COMPENSATION. The manual (p.198) specifies the loss rather than merely permitting
     it — "the amplitude of the passband will drop about 12 dB when the resonance is set to a high
     value" — and the engine had been putting a quarter of it back, i.e. gain the hardware never
     applies, exactly where a patch is most likely to be driven hard. Now measures an 11.2 dB drop
     against the manual's ~12.
   * SMOOTH SATURATION INSTEAD OF A HARD CLIP on the stage input: y = x - x^3/3, held flat outside
     +/-1. Unity slope at the origin so quiet signals are untouched; it rounds the resonance peak
     rather than tearing it, and it is what bounds self-oscillation. The manual's own description of
     this filter is a "classic analog" ladder with a "more narrow resonance peak", which is the
     behaviour a saturating feedback path produces.
  THE TEST NOW ENCODES THE SPEC, NOT THE IMPLEMENTATION. test_filter's passband check was a one-sided
  floor (0.6, then 0.45 as the compensation shrank), which could only ever catch too MUCH loss —
  while the actual defect for months was too LITTLE. It is now a BAND of roughly 6..16 dB, so
  compensation creeping back fails the test. New test_fltclassic covers the 12 dB figure, saturation
  under drive, and bounded self-oscillation.
  NOT COMPARED AGAINST HARDWARE AUDIO — the target came from the manual's stated figure, not from a
  capture of the real filter. A recording of the same patch through the G2 would settle whether the
  resonance mapping and the saturation depth are right, which the 12 dB figure alone does not.

- Sound engine dial curves are COMPUTED for the audio path — owner's call 2026-08-05: "compute
  should be for what we hear". The tables stay as the DISPLAY's business.
  THE REASON THIS MATTERS MORE THAN ACCURACY: morphs and the parameter smoothing both produce
  FRACTIONAL dial values, and a table index truncates them — so a morphed or swept envelope time
  stepped between whole dial positions instead of moving continuously. Computing fixes the stepping,
  not just the error.
   * A/D/R times: t = 1.015839e-16 * (v + 39.55)^7.94210. A POWER LAW, not the exponential one would
     reach for first — the ratio between neighbouring table entries falls from 1.20 to 1.049, which
     is what gives it away. Median error against the table 0.35%, worst 4% at index 2 where the
     TABLE carries one significant figure ("0.7ms"), so the formula is arguably the more accurate of
     the two there. The exponential this replaced was out by 86% mid-range.
   * Glide: INTERPOLATED between table entries instead, because that table has no decent closed
     form — the best power-law fit is 17% out at the median and 38% at worst, far worse than reading
     it. Interpolation gives the same continuity without inventing a bad curve.
  TO NOTE, owner's request: the DISPLAY could be made more accurate in its own right at some point.
  ADRTimeStrMap and patch_settings_glideStrMap are rounded strings — as little as one significant
  figure at the short end — so the dial currently reads less precisely than the engine now plays.
  A display derived from the same curve (or simply more decimal places) would close that.

- Filter resonance too weak — FIXED 2026-08-05, owner reported the engine less resonant than the
  hardware on the same patch. IT WAS A SIDE EFFECT OF THE OVERSAMPLING. The textbook feedback of 4
  is for a ladder with NO delay in its loop; this one has a sample of it, and how much phase that
  sample contributes depends on the sample rate — so moving the engine to 96 kHz pushed the loop
  further from oscillation and took the resonance with it. Nothing about the filter changed; the
  rate did.
  MEASURED, peak gain from Res 0 to Res 127 at a 1.4 kHz cutoff, 12/18/24 dB slopes:
      k 3.9 -> +16/+21/+24 dB     k 5.0 -> +79/+81/+73 dB     k 6.0 -> +82/+85/+86 dB
  3.9 barely resonated. Past about 6 the knob's useful travel collapses into its last few steps.
  LADDER_K_MAX is now 5.0, and self-oscillation with no input at all goes from 0.0055 to 0.034.
  RE-MEASURE IF ENGINE_OVERSAMPLE CHANGES — the constant is a property of the RATE, not the filter.
  A TEST HAD TO GO, and it is worth saying why rather than it looking like a threshold being bent:
  test_filter asserted the passband drop from OVERALL rms, which was only ever a proxy. Once the
  filter properly resonates the peak dominates that figure — 91% of the energy now sits near the
  cutoff — so it no longer measures the passband at all. It is reported but not asserted; the real
  measurement is in test_fltclassic, which places a tone well below the cutoff and still checks it
  against the manual's stated ~12 dB (now reading 14.9).
  SLOPES: 12/18/24 dB are implemented by TAPPING stage 2, 3 or 4 of the ladder while the feedback
  always comes from stage 4 — a two-pole loop cannot reach the 180 degrees it would need to resonate,
  which is how a real ladder's multimode outputs work too.

- WHOLE-GRAPH OVERSAMPLING — done 2026-08-05, the proper fix the raspiness entry below asked for.
  ENGINE_OVERSAMPLE 2, so the graph runs at 96 kHz for a 48 kHz device, which is exactly what the G2
  does (manual p.71: audio at 96 kHz). gSampleRate IS the internal rate, so every coefficient
  already derived from it — envelope and glide times, filter and chorus coefficients, LFO and
  oscillator increments — scaled with no further change. One windowed-sinc decimator (64 taps) at
  the very output; nothing else in the graph knows it is happening.
  WHY WHOLE-GRAPH RATHER THAN PER-NODE: only the nonlinear parts actually need it (the ladder and
  its saturation, LevMult as a ring modulator, the compressor), but doing it per node means
  interpolating an input and decimating an output for each of them. One rate throughout is simpler,
  and the linear parts cost little.
  WHAT HAD TO CHANGE, all of it because these are counts of SAMPLES rather than times:
   * DELAY_LINE_SAMPLES — and it was ALREADY WRONG: a flat 48000, i.e. one second, against a Time
     dial that offers up to 2.7 s. Long delays were being silently truncated to well under half.
     Now 2.8 s at the internal rate.
   * CHORUS_SAMPLES, and the reverb comb/allpass lengths — fixed sample counts that would otherwise
     have halved the room.
   * OSC_OVERSAMPLE is now relative to the engine rate (4 / ENGINE_OVERSAMPLE), so the oscillators
     still run at four times the DEVICE rate overall, as before.
  RESULT: the filter is clean across the entire cutoff range — 59.8 dB of margin at every setting,
  where 17.7 kHz previously measured 31.8. The internal coefficient at the very top of the dial is
  now 0.728, inside the model's valid region, so LADDER_MAX_G no longer engages at all within the
  dial's range and the full range is usable again. The clamp is kept as a guard for lower device
  rates or if the oversampling is ever turned off.
  COST: CPU 1.8% -> 3.4% of the real-time budget on a 12-module patch. Memory: the delay lines are
  now ~4 MB.
  NOT VERIFIED BY EAR. All 14 suites pass and the delay still measures 496 ms, i.e. timings survived
  the rate change — but nobody has listened to it.

- Filter raspiness at high cutoff — FOUND AND FIXED 2026-08-05 from an owner report: full resonance
  at 17.7 kHz, no env, Kbt off, sounded raspy where the G2 is smooth.
  IT WAS THE SATURATION ADDED THE SAME DAY. Isolating it settled the cause immediately: with the
  cubic in, non-harmonic content sat 32 dB below the note; with it removed the filter DIVERGED to
  NaN instead, which is what the saturation was there to prevent. So neither the old code nor the
  new was right — the model itself breaks down up there.
  MEASURED, sweeping cutoff at full resonance and reading the margin between the note and the worst
  non-harmonic content:
      g 0.728  60 dB    g 0.806  60 dB    g 0.842  53 dB    g 0.874  32 dB    g 0.902  32 dB
  Below g = 0.806 it is clean; by 0.874 the margin has collapsed AND the passband has dropped 6 dB,
  i.e. the filter is misbehaving rather than merely distorting. Each ladder stage is a one-pole
  using the previous sample's output, and four of them in a feedback loop stop behaving as a filter
  once the poles approach Nyquist.
  THIS IS A CONSEQUENCE OF RUNNING AT 48 kHz. FltClassic reaches 21.1 kHz (manual p.198), which at
  the G2's own 96 kHz gives half this g and sits well inside the model. The same dial at 48 kHz does
  not. FIXED by clamping g to LADDER_MAX_G 0.80 — the whole dial now measures 59.9 dB of margin.
  The cost is that cutoff stops climbing near the very top, where a 24 dB/octave lowpass is close to
  transparent anyway.
  ALSO: ladder_saturate() is now LINEAR BELOW A KNEE (0.7) instead of curving on every sample. An
  always-on nonlinearity generates harmonics on every sample, and this filter is not oversampled, so
  they fold. Only a genuinely driven signal is shaped now.
  THE PROPER FIX IS TO OVERSAMPLE THE FILTER, as the oscillators already are. That would restore the
  top of the cutoff range and remove the folding at source, and it is the difference between this
  and the hardware.

- Sound engine parameter smoothing — 2026-08-05, after the owner heard ZIPPER NOISE sweeping Shape
  between triangle and saw where the G2 is smooth.
  THE CAUSE IS THE UPDATE RATE, NOT MISSING SMOOTHING ON THE HARDWARE'S PART. The G2 runs modulation
  at 24 kHz (manual p.71: "modules can process and output signals at two sample rates: 96kHz and
  24kHz", the lower one for modulation), so a dial arrives at its DSP finely stepped and needs no
  smoothing of its own. This engine rebuilds its parameter snapshot ON A REDRAW, i.e. at frame rate
  — a few hundred times coarser — and a stepped parameter is audible, most obviously on Shape where
  each step moves the waveform itself.
  FIXED by interpolating per sample toward the snapshot value (PARAM_SMOOTH_SECONDS 0.008) for the
  continuous parameters: shape, filter cutoff and resonance, gains and mixer levels. Discrete things
  are deliberately NOT smoothed — waveform, slope, curve, active flags — since interpolating an
  index is meaningless.
  gSmoothPrimed[] snaps the first sample a node is seen rather than interpolating from whatever the
  previous patch left in that slot, so a patch load is still instant.
  MEASURED: largest sample-to-sample jump across a full Shape sweep is 0.021, i.e. below the
  waveform's own per-sample motion — no step stands out. CPU went DOWN slightly (1.8% from 2.2%),
  the smoothing being cheaper than the noise it removes is coincidence, not causation.
  WORTH KNOWING: this only smooths what the snapshot carries. A parameter that changes discretely
  by design (waveform, slope) will still click, as it does on the hardware.

      sends every level to +100 dB and over. Normalise by the strongest harmonic; the comparison is
      of spectral SHAPE.

--- 2. DONE 2026-08-07, but the diagnosis above it was OVERSTATED — read this before trusting it ---

The claim was that our modulation is the wrong SHAPE: ours multiplied the cutoff by
pow(2, mod*modAmount*64/12) while the hardware sums into a normalised control domain and clamps.

THE SHAPE WAS NEVER WRONG. flt_cutoff_hz() is 13.75 * 2^(value/12) — the Freq dial is a PITCH,
counting semitones up from A-1 to 21.1 kHz at 127 (manual p.198). Because the dial is itself
logarithmic in frequency:

    flt_cutoff_hz(P) * 2^(s/12)  ==  flt_cutoff_hz(P + s)        identically, for any s

so "multiply the frequency by 2^(semitones/12)" and "add semitones to the control value" are the
same operation written two ways. Chasing a shape difference here would have been chasing nothing.
The real defect was narrower and entirely real: THERE WAS NO CLAMP, because the frequency domain
offers no natural place to put one.

DONE: filter_step() now keeps the Freq dial value (tEngineNode.cutoffParam, no longer cutoffHz),
sums Env modulation and Kbt into it in dial units, clamps to 0..127, and converts once via
flt_cutoff_hz(). Parameter smoothing moved to the dial domain with it — smoothing a log control
linearly in hertz crawls at the bottom of the travel and leaps at the top.

FULL_MOD_SEMITONES stays 64 and should not be retuned: modAmount reaches 2.0 (the dial's 0..200%),
so 64 * 2 = 128 semitones is exactly the dial's full range. The two constants multiplying out to
the range is the reason to believe 64, rather than fitting a number to make the old unclamped
arithmetic behave.

MEASURED (headless, both engines built from the same harness, SimpleLead.pch2):
  - Ordinary settings are BIT-IDENTICAL. Freq=40/Env=1.0 across a full envelope sweep: same hertz,
    same g, every step. This is the algebraic identity above showing up in the audio.
  - Over a 3456-point grid the two differ at 26% of points, ALL of them clamped: at the top of the
    dial (the audible ones) or at the bottom, where nothing above 13.8 Hz is ever involved and a
    24 dB/oct lowpass is shut anyway.
  - The g clamp (LADDER_MAX_G) fired at 23% of grid points before and NEVER now. That was the real
    problem: the instrument's ceiling was being set by a safety limit on the filter model at
    whatever frequency it happened to bite (~24.6 kHz), not by the dial's 21.1 kHz.
  - In the clamp region the new code is LOUDER AND BRIGHTER despite the lower ceiling — peak
    -22.03 -> -21.41 dBFS, zcr 799 -> 835 Hz. Old g was pinned at 0.80, where this function's own
    measurements say the passband has dropped ~6 dB; new g is 0.749, inside the model.

STILL NEEDS AN EAR. Everything above is numerical. The knob-turn behaviour in particular changed
(smoothing domain) and cannot be measured from steady-state renders.

CORRECTION to the reference reading, for whoever goes back to it: CNativeFilterCoeffsPart::Compute
is NOT the frequency conversion this section claimed. It computes x + Q23mul(x, y) and stores a
pair — a coefficient smoother/interpolator. Do not go looking for cutoff-to-hertz constants in it.
Also note CNativeFilterModPart clamps the sum AFTER a *4, so the effective bound on the sum is
+/-0x200000, not +/-0x800000; that detail was not needed here but will matter if anyone tries to
match the hardware's modulation depth exactly.

--- 3. CLEARED 2026-08-07: the filter coefficient rate is CORRECT, this was not a bug ---

The suspicion was that filter_step computes g = 1 - exp(-2*pi*cutoff / gSampleRate) against an
oversampled gSampleRate while the filter itself runs at base rate, making the cutoff several times
too low. It does not. THE WHOLE GRAPH RUNS OVERSAMPLED, not just the oscillators (ENGINE_OVERSAMPLE
is 2, soundEngine.c:465):
  - sound_engine_set_sample_rate() sets gDeviceRate 48k, gSampleRate 96k — gSampleRate IS the
    internal rate by definition.
  - sound_engine_render() wraps the entire node graph in for (sub < ENGINE_OVERSAMPLE), :2854-3119,
    and filter_step is called INSIDE it at :2952. The output decimator runs after, once per frame.
So the filter is evaluated at 96 kHz and its coefficient is derived from 96 kHz. Rate matches; no
4x error and no 2x one. OSC_OVERSAMPLE = (4 / ENGINE_OVERSAMPLE) keeps the oscillators at 4x the
device rate on top of that. The VST3 passes the host rate straight in (g2Vst3.cpp:287), so the
plug-in's filter is no darker than the app's — its shut filter is entirely section 1.

STALE COMMENT, worth fixing when the filter is next touched: the block at soundEngine.c:2779 still
says the LADDER_MAX_G clamp is "a consequence of running at the OUTPUT rate" and that "the real fix
is to run the filter oversampled". That describes the pre-ENGINE_OVERSAMPLE engine. The clamp may
now bite earlier than it needs to at 96 kHz, but that is range at the very top of the dial, not
tone across it.

  work measured the G2 as carrying 8x (18 dB) between a nominal module output and DSP saturation,
  which makes the principled value 1/8 = 0.125: nominal lands at 0.125 and saturation arrives at 8x
  nominal, reproducing the hardware's relationship instead of a trim. The code went 0.25 -> 0.15 in
  commit 58e0725 with no derivation recorded anywhere. So the decision is smaller than it looks —
  mostly "adopt 0.125, or say why not" — but it is a ~1.6 dB level change and wants an ear.
- Polyphony: Voice Area is per-voice, FX Area is global. Needs node state split by area
  ([MAX_VOICES][MAX_ENGINE_NODES] for VA nodes, single-instance for FX), a voice allocator honouring
  gPatchDescr[slot].voiceCount, and per-voice glide/note queue. The VA-Out -> FX-bus link the engine
  now models correctly is already the right join point.
- Module coverage: ~17 of the G2's modules. FltLP added 2026-08-07 with a per-module filter param
  map (it has NO resonance, so its Slope sits one index earlier than FltClassic's — blind reuse
  would read a menu index as a resonance value). Extend that map per module; read indices, never
  assume them.

  FltHP: STILL NOT ADDED, but the stated reason was wrong (checked 2026-08-07). Its params were
  dumped straight out of paramLocationList in ordinal order rather than read off the file, and
  FltHP HAS NO SLOPE PARAMETER AT ALL — it has four: [0] Freq (type 1), [1] FreqMod (type 25),
  [2] Kbt, [3] Bypass (type 16, the same signature as the other filters' active flag). There was
  nothing 1500 lines away to confirm. Its map would be {0, 1, 2, -1, -1, 3}.

  THE REAL BLOCKER IS THAT THE ENGINE HAS NO HIGHPASS. eNodeFilter routes to filter_step() ->
  ladder_filter(), which is a lowpass; FltClassic and FltLP are both lowpass, so nothing has needed
  one yet. Adding FltHP to the map alone would render a highpass as a lowpass — a patch that should
  sound thin would sound dark. That is worse than the silence it renders now, because silence is
  obviously broken and a wrong-mode filter is plausible and wrong. Add the highpass first.

  Worth knowing for that work: dumping paramLocationList in ordinal order for a module type is the
  reliable way to build one of these maps, and takes about ten lines against
  array_size_param_location_list(). Do that rather than reading moduleResources.h.

- Load Perf from Bank — FIXED 2026-08-05 from an owner log, needs a confirming run. TWO faults, both
  in the perf domain that had been left unverified when the patch case was fixed:
   1. THE FIRST PAYLOAD BYTE IS A SLOT, and the perf path was sending the bank-upload DOMAIN value
      there — which is 1, i.e. slot B. The performance is addressed as slot MAX_SLOTS: that is
      already how parse_patch_version() reads it, where slot == MAX_SLOTS carries the PERF version
      rather than a slot's. Both send_store_patch() and send_retrieve_patch() now send MAX_SLOTS.
   2. IT WAS WAITING FOR THE WRONG REPLY. A performance load changes all four slots at once and the
      G2 answers with SUB_RESPONSE_PERF_PATCH_VERSIONS (0x1f), not the single-slot
      SUB_RESPONSE_PATCH_VERSION_CHANGE (0x38). The log made this unmistakable — "response = 0x1f
      expected = 0x38", three times, with the patch versions climbing 33/34/35 as each retry
      RE-SENT the retrieve. So the load had been working all along; the editor rejected the reply
      and then loaded the performance three times over before reporting failure.
  3. THE PERFORMANCE NAME DID NOT UPDATE after a successful load, because nothing re-read the perf
     settings. parse_perf_patch_versions() raises gotPerfSettingsChangeIndication ONLY when the perf
     VERSION changes, and a load does not necessarily change it — the log of a working load reads
     "Old perf = 8 new = 8", so the refresh never fired and the previous name stayed on screen.
     load_patch_from_bank() now calls send_get_performance_settings() after a successful PERF
     retrieve. Note this is safe here but is deliberately NOT done in load_perf_from_payload() (the
     file-load path), where the settings are about to be overwritten from the file and reading the
     device would pull the OLD perf's data over them — the comment there explains it.
  WORTH REMEMBERING: a send_and_receive() expectation that does not match reality does not merely
  mis-report — the retry re-sends the command, so a "failed" operation can happen several times.
  ALSO: a version-change flag is not a substitute for "this operation changed things". Any refresh
  hung off gotPerfSettingsChangeIndication silently does nothing when the version happens to match.
  STILL UNVERIFIED: the perf domain of send_store_patch(). It is a flash write, so test on a
  scratch location; its expected reply (SUB_RESPONSE_STORE_PATCH) may need the same treatment.

  clash with it turned dials into blank white squares, and it hid exactly the button text the view
  was meant to annotate. What makes going maskless work is that THE CHIP NEVER REPEATS WHAT THE
  WIDGET ALREADY SHOWS: it carries the raw wire value alone, so it stays two or three characters
  wide. Raw and formatted still end up next to each other as in the original - the formatted half
  just comes from the control itself.
  Placement follows from the same idea: centred on a dial, which has nothing inside its circle to
  collide with, and in the TOP-LEFT CORNER of a widget that carries its own text, where centring
  would land the chip across the word ("Semi" under a "0" reads as "S0mi"). The caller handing
  over a non-empty display string is what distinguishes the two.
  WHAT THE VALUES VIEW SHOWS: the raw wire value always, and the formatted value ONLY where the
  box has covered it. Since dials became dial-anchored the mask covers just the circle, so a
  dial's own "Pitch / 0.0" is still on screen above the box and repeating it would print the same
  string twice; a button's text IS its value and is covered, so that one is reproduced.
  Z-ORDER: param_overlay_render() runs immediately after the modules and cables, BEFORE the top
  bar, menus and every panel - it used to run near the end of the frame, which let it paint over
  open menus.

  THE FIRST VERSION LANDED ONLY SOMETIMES, and the reason generalises to any future bulk operation
  on this device. Every slot command is stamped with the slot's patch version by usb_cmd_slot()
  (usbComms.c), and that version is only ever refreshed when the G2's ASYNCHRONOUS
  SUB_RESPONSE_PATCH_VERSION_CHANGE (0x38) notification is parsed — nothing bumps it locally after
  a send. int_rec() returns the moment it sees the expected SUB_RESPONSE_OK and does not drain
  what else is pending, so in a burst, command N+1 races the version bump from command N and the
  G2 rejects whichever loses. It was silent because send_assign_midi_cc()'s return value is
  discarded by its caller and the local table had already recorded the change — so the UI showed
  CC#s the device never accepted. Single right-click assigns never hit it: one command, with idle
  time either side for the 0x38 to arrive.

  (protocol.c) already serialises the entire controller table, so all 120 assignments cross in a
  single versioned command and there is nothing to race. eMsgCmdWritePatch was already used this
  way from the UI thread for something as ordinary as a patch-notes edit (mouseHandle.c,
  mousePanels.c) — no synth stop, no ceremony.
  UNDO SURVIVES, and was in fact broken the same way before this: apply_midi_cc() (undo.c) replayed
  the same burst of per-entry deassign/assign commands, so Ctrl-Z after a sweep landed only partly.

  NOTE ON/OFF CONFIRMED ON HARDWARE 2026-08-02, after one real bug: THE FLAG BYTE IS INVERTED FROM
  THE OBVIOUS READING. ZERO SOUNDS THE NOTE, ONE RELEASES IT. Sent as 1-for-on first, which gave a
  keyboard that was exactly backwards — silent on press, sounding on release. So CMPlayNote::
  EAction's value 1 is the note-OFF action and the reference's `action == 1` is asking "is this a
  release?", not "is this a press?". Nothing in the reference says which way round the enum runs;
  only the hardware did. A good example of why a reference settles the SHAPE of a message but not
  its polarity.

  missing note-off, and the UI path was suspected first. It was traced and cleared —

- ASSIGN MIDI CC WIRE FORMAT CONFIRMED 2026-08-05 from an owner USB capture of the ORIGINAL editor

  THE CURVE, decoded from CPatch::ApplyDistribution() in the reference — knobs run -50..+50 with 0
  at centre, working from a BASELINE snapshot rather than from live values:
      amount > 0:  new = orig + (max - orig) * amount/50      (toward maximum)
      amount < 0:  new = orig * (50 + amount)/50              (toward zero)
      amount == 0: untouched

  to centre restores its category exactly, and several knobs can be off-centre at once without
  fighting, since each owns a disjoint set of parameters.

  patch-version race to lose. Only parameters whose computed value actually CHANGES are sent, which
  is the original's own test and matters because a Timbre sweep over a dense patch touches a lot.

  WHERE "LAST RECEIVED" COMES FROM — REWORKED 2026-08-05 after the owner pointed out the obvious:
  THE SYNTH IS THE THING WITH A MIDI IN SOCKET, so in the setup the manual describes it is the G2
  that sees the controller and the editor never does. Learning from the editor's own CoreMIDI input
  only works when the controller is plugged into the Mac. Both are now accepted, synth first.
  The synth side goes through SUB_RESPONSE_MIDI_CC (0x80), which parse_midi_cc() has always decoded
  into a channel and a CC byte and then THROWN AWAY. Now recorded.
  TWO REAL BUGS FIXED HERE:
   * 0xff IS A SENTINEL meaning "nothing to report", and it was being stored as though it were CC
     255. Controller numbers stop at 127, so anything above that is now rejected. This is what the
     owner saw as "thinks the last CC received was 255" — it was the reply to the request issued at
     CONNECT, before any controller had been touched.
   * THE REQUEST WAS ONLY EVER SENT AT CONNECT (send_get_midi_cc(), usbComms.c:3469/3528), i.e.
     exactly when the answer is guaranteed to be "none". New eMsgCmdGetMidiCC lets the UI ask again.
  L NOW COMPLETES ASYNCHRONOUSLY when online: the press parks the target parameter, posts the
  request, and midi_learn_poll() (once a frame, from render_frame) finishes the assignment when a
  FRESH reply lands — freshness being a rise in the arrival count, not merely a non-negative value,
  since the previous answer is still in hand. Gives up after ~2s and logs that the synth reported
  nothing. The param right-click menu re-requests as it opens and names its source, so the label
  reads "Assign to CC# 74 (last, from synth)" or "(from MIDI in)".
  SETTLED 2026-08-05 BY AN OWNER USB CAPTURE of the original editor doing a Learn (new patch, all
  MIDI deassigned, one filter, controller into the G2's MIDI IN, dial moved, parameter clicked, L
  pressed). THE G2 PUSHES IT UNSOLICITED — nothing is requested:
      t=3.722  G2 -> editor   82 01 04 00 80 00 10 e5 cd
                                          ^^ ^^ ^^
                                     sub=80  chan=00  cc=10
      t=19.213 editor -> G2   00 0c 01 28 01 22 01 01 07 10 79 3d      (ASSIGN, cc=10)
  So SUB_RESPONSE_MIDI_CC arrives on its own when the synth receives a CC that is assigned to
  NOTHING, carrying the channel and then the controller NUMBER — which also settles the old
  "CC Numb/value" ambiguity in parse_midi_cc(): it is the NUMBER. The editor just remembers it, and
  the Learn is a single assign command with no query anywhere in it.
  SUB_COMMAND_GET_MIDI_CC'S REPLY IS ONE RECORD PER SLOT — the owner spotted it from a clean log
  showing exactly four records, the first carrying CC 20 and the other three 0xff. So it is the last
  CC EACH SLOT has seen, not a list of assignments, and 0xff means that slot has seen none. It is
  what makes Learn work immediately after the editor starts, instead of demanding the controller be
  moved again. gLastDeviceMidiCC is now per slot and midi_learn_last_cc() reads the current one.
  (An intermediate version treated this reply as assignments and DISCARDED it, which was wrong for
  the same reason the very first version was wrong — it is the useful message, not the noise.)
  IT HOLDS SEVERAL RECORDS SEPARATED BY A REPEAT OF THE 0x80 SUB-RESPONSE BYTE, while the
  unsolicited notification is a single record with no separator. A flat two-byte stride walked the
  reply out of step, which is how it announced itself: "channel 129", i.e. a 0x80 separator read as
  a channel. The loop now consumes a separator between records and stops when the next byte is not
  0x80, and files each record by POSITION when solicited, by the message's own slot when not.
  STILL UNSETTLED: whether the first byte of a record is the MIDI CHANNEL or the SLOT. Every sample
  so far has 0 in it, so nothing distinguishes them; it is logged, not used. If it is the slot, the
  0xff records will carry 1, 2 and 3 — which the next connect log will show.
  A MIDI CHANNEL IS 0..15, so a channel byte above 15 now aborts the walk with an error rather than
  reporting invented controllers — every value after a desync is worthless and MIDI Learn would
  otherwise take the last of them. Worth applying wherever a parser has a field with a known range.

  THE REASON IT HAD NEVER WORKED, found by the owner reading parse_midi_cc(): its loop guard asked
  for THREE bytes (`(BIT_TO_BYTE_ROUND_UP(bitPos) + 3) <= length`) while the payload is TWO, so the
  loop never ran and the message was parsed into nothing. Two separate mistakes in the same loop:
    * the guard did not match the body, which read channel + controller + a trailing byte it hoped
      would be another 0x80 marking a further record;
    * there is no marker byte. The capture is 82 01 04 00 80 00 10 e5 cd — sub-response, then the
      two-byte payload, then the CRC. The third read was taking the CRC (seen as 0xa5 in the log).
  Now `(... + 2) <= length`, and the trailing read is gone. Note the guard must require a WHOLE
  record rather than merely a byte remaining: `< length` happens to work for a lone two-byte payload
  but would let a stray trailing byte start a record that reads past the end.

  CONSEQUENCE: the poll-the-synth-on-L machinery built earlier the same day was the wrong shape and
  has been REMOVED (eMsgCmdGetMidiCC, request_synth_last_cc(), midi_learn_poll() and its per-frame
  call). L assigns synchronously from the value parse_midi_cc() has already recorded, exactly as the
  original does. send_get_midi_cc() at connect is untouched — it is pre-existing and harmless.
  WHAT REMAINS UNPROVEN: whether 0x81 answers anything useful. It might instead be the stored assignment TABLE — parse_midi_cc() loops over
  MULTIPLE records, which fits a table better than a single last-received value, and the name says
  "GET_MIDI_CC" rather than anything about receiving. No dedicated learn command exists among the
  SUB_COMMAND_* constants (checked: the only never-sent ones are CLEAR_BANK, MIDI_DUMP,
  QUERY_PARAM_NAMES, QUERY_PARAMS, SET_ASSIGNED_VOICES, SET_KEY_SPLIT, SET_PERF_MODE — none of them
  plausible). THE TEST: with a controller into the G2's own MIDI IN, move one control, then press L
  or right-click a parameter. If the CC appears, 0x81 is the right question. If it stays "No MIDI CC
  received yet" while the synth is plainly receiving, then the G2 does not report received CCs this
  way and the feature needs a different message — which would want a USB-log capture of the real
  editor doing a Learn to settle.
  NOT VERIFIED, and it cannot be through the harness: synthetic KEY events do not reach the app at

     THE UNIT IS PIXELS, not a fraction. The reference's layout code computes
     the top pane's bottom edge as toolbarHeight + scrollBarHeight + splitterPos, clamps it to the
     window less the scrollbar less 11, and gives the bar itself a height of 0xb = 11 px. So
     splitterPos IS THE VOICE AREA PANE'S HEIGHT IN PIXELS.
     DESIGN CONSEQUENCE, and it needs an owner decision. tSplitView.divider is a FRACTION of the
     canvas band, which redistributes proportionally on a window resize. The stored value is pixels,
     which does not — the original keeps the top pane's pixel height and lets the bottom absorb the
     change, clamping when it runs out. Two options:
       (a) PIXEL-FAITHFUL: make barPosition the source of truth and derive the fraction each frame.
           Round-trips exactly, matches the original's resize behaviour.
       (b) PROPORTIONAL: keep the fraction internally and convert at the protocol boundary using the
           current band height. Nicer on resize, but the stored value then depends on the window
           size at the time, which is a lossy round-trip.
     Leaning (a) for parity and exactness.
     ALSO: the original's default for a NEW patch is SetSplitterPos(4000) — far larger than any real
     window, so it clamps to "voice area takes everything". G2-Edit's new-patch default is 600
     (mouseHandle.c:127), i.e. a ~600px voice area. Worth aligning to 4000.
     And the original's bar is 11 px; ours is SV_BAR_H = 14.
   * Module drag, rubber band and cable drag are NOT yet clamped to their originating pane. Starting
     a drag in one pane and crossing into the other is currently undefined and is the next real
     hazard to close.
   * A patch with genuine FX-area content still needs loading to see the two areas side by side for
     real.

  WHAT EACH COMMAND DOES NOW:

     neighbour becomes the new parent (the connector's own parent; the first child when the
     connector is the chain root, i.e. an output), and every other neighbour reattaches to it.
   * BREAK — unchanged in behaviour, refactored onto the shared layer. Still a no-op on a
     sourceless chain, still whitens the dead tail.
   * COLOR — now applies to the BRANCH (was: cables touching the clicked connector). Refused on a
     sourceless chain, because white is a state, not a user colour.
   * DELETE — new. Branch-scoped: the cable feeding the clicked connector plus its whole subtree.
     Matches "if you want to delete a complete branch connection, this must be done from the cable
     origin of the branch".
   * DELETE UNUSED CABLES — new. Patch-wide sweep. Computed from LIVE source-reachability rather
     than from the stored colour, since a patch loaded from a file or from a G2 written by an older
     build can carry a colour that predates the invariant, and this is not undoable.

- White cables — RULE IMPLEMENTED 2026-07-31, previously only understood. The invariant is:
      every cable in a chain shares ONE colour = the source output's signal-type colour,
      or WHITE (6) if the chain has no source output at all.
  MapConnectorColorToCableColor can never return 6; white only ever appears as the literal 6 on the
  no-chain-ID branches. That is what makes white unambiguously mean "this chain has no source".
  Colour is STORED and USER-OVERRIDABLE (the COLOR menu offers green and purple, which no signal
  type produces), so the recompute is conditional on SOURCE-REACHABILITY CHANGING, never
  unconditional — a blind recompute after every edit would destroy the user's colour choice.
  The minimal case that motivated all this now works: on a new patch, linking two mixer inputs to
  each other produces a WHITE cable immediately, because the new cable's chain has no source.
  Previously G2-Edit showed it red, a state the original cannot represent.
  Unit-tested headless (32 assertions over the shipped functions: white-on-sourceless, whole-tree
  repaint on connect, branch vs tree scope, Break's no-op and whitening at both an input and an
  output, Disconnect's splice at mid-chain and at the root, and the unused sweep). The harness is
  NOT in the repo — it lives in the session scratchpad and links cableChain.c / dataBase.c /
  moduleResourcesAccess.c with a stubbed msg_send. Worth reconstructing if this area is touched
  again; there is no test target in the Xcode project to host it.

- Bit-stream loop guards audited 2026-08-05, after the parse_midi_cc() bug (see MIDI Learn above).
  THE PATTERN TO LOOK FOR: a loop guard that asks whether ANY bytes remain while the body reads a
  whole RECORD. It fails in both directions — a payload smaller than the body's appetite is skipped
  entirely (which is what hid every received CC), and a truncated one is read past.
  FOUR LOOPS CARRIED IT. All now require the bytes they are about to read:
   * protocol.c parse_patch()  — guard covered the 1-byte type, body then read a 16-bit count.
   * protocol.c parse_perf()   — same.
   * protocol.c (category scan) — same, breaks out instead of failing.
   * usbComms.c parse_resources_used() — guard wanted 1 byte, the record is a fixed 29
     (RESOURCES_RECORD_BYTES, tallied in a comment there).
  The three TLV ones already bounds-checked the VALUE after reading the count; it was the header
  itself that was unguarded, so the overrun was at most two bytes and into the same buffer — wrong
  values rather than a crash, which is why it has gone unnoticed.
  VERIFIED: all nine PatchTestFiles still load with their expected module counts, and Corrupt.pch2
  still fails deliberately (0 modules) rather than being newly rejected for the wrong reason.
  NOT AUDITED YET: the many straight-line parsers that read a fixed layout without looping. They
  cannot loop past the end, but nothing checks `length` against what they read either.

- Reconnect clobbers offline edits — BUILT 2026-08-01, mostly hardware-verified. Kept below for the
  reasoning; what shipped is at the end of this entry.
  Original report (2026-07-31): edit a patch with the G2
  unplugged (entirely normal, and the backdoor test channel exists precisely to drive the app
  offline), then plug the G2 in: the app fetches the synth's patch and overwrites the in-memory
  database, and the offline work is gone with no warning and no way back.
  PREREQUISITE, and probably most of the work: G2-Edit HAS NO DIRTY TRACKING. Nothing matching
  gDirty/isDirty/modified/unsaved exists anywhere in src/. Without a notion of "the editor's copy
  has diverged from the synth's" there is nothing to base any prompt on, and a prompt that fires on
  EVERY reconnect regardless would just be a nag people learn to dismiss — which is worse than
  useless, because they will dismiss the one that mattered.
  THREE CANDIDATE BEHAVIOURS (owner raised A and B; C is a suggestion):
   A. ASK WHICH WINS — "keep the synth's patch" vs "push the editor's patch to the synth". Best
      ergonomics, but the second branch is a destructive write to the synth's edit buffer, so it
      needs the same care as the Bank Restore work.
   B. OFFER TO SAVE FIRST — save the editor's patch to a file, then load the synth's. Strictly
      safer, and maintains both, but it is a save dialogue at an awkward moment and it does not let
      you carry on working on the editor's version, only archive it.
   C. AUTO-PRESERVE, DO NOT ASK — always write the editor's patch to a recovery file, load the
      synth's, and just report "your edits were saved to <path>". No modal decision at the moment
      someone has plugged in a cable, and nothing is ever lost. Cheapest to build once dirty
      tracking exists, and it degrades gracefully: if the divergence did not matter, the user
      ignores the message.
      A and C combine well — auto-preserve ALWAYS, and additionally offer the choice only when the
      editor's copy is actually dirty.
  OPEN QUESTIONS: is dirty tracked per SLOT (there are 4 plus the performance) or per patch, since
  a reconnect reloads everything and the conflict may only affect one slot? And discarding the
  editor's patch must clear the undo history, which would otherwise let Ctrl-Z "undo" into a state
  that never existed on the synth — ties into the undo sweep entry above.
  SCOPE NOTE: this is not really about reconnect. It is the general "editor copy has diverged from
  the synth copy" problem, and the same conflict exists on slot change and on any other reload from
  the device. Worth solving once, generally, rather than special-casing the reconnect path. The
  mechanism below is reusable for those, but is currently wired to the reconnect path only.

  WHAT SHIPPED (owner chose A + C: auto-preserve, then ask):
   * DIRTY TRACKING TURNED OUT TO BE FREE. While online every edit is sent to the G2 as it is made,
     so the copies can only drift while it is away — and those edits are already recorded in the
     USB command queue, which state_handler() only drains when online. Anything sitting in it at
     reconnect was enqueued while the G2 was gone, and each message carries its slot. So the drain

   * THE PULL IS DEFERRED, not done-then-regretted: new eCommsAwaitingSyncDecision state parks the

   * RECOVERY FILE FIRST, then the dialog: one .pch2 per dirty slot in

ARCHITECTURE — RATIONALISE AND COMMONALISE FOR THE OTHER PROJECTS

***PRIORITY*** (identified 2026-07-25 by diffing G2-Edit / EmuUtility / SynthEdit directly — concrete,
mostly-mechanical dedup + decoupling wins at the host<->SynthLib boundary; do these before the bigger
open design items below):

1. [PRIORITY] Shared graphics/window bootstrap. init_graphics() and every window callback
   (framebuffer_size_callback / content_scale_callback / window_size / window_pos / window_close) are
   ~90% character-identical across all three apps: same glfwWindowHints, same glfwCreateWindow, same
   context/FreeType/scale init, same callback wiring. Only real differences: dial-mode default,
   topBarHeight, whether wake-callbacks are registered, and the callback function *names* (key_callback
   vs key_cb — a non-issue, they go in a struct). There is already a precedent seam (apps pass
   configure_synthlib_theme((tSynthLibTheme){...}) — utilsGraphics.h). Extend it:
       tGlfwWindow * synthlib_window_create(const tSynthLibWindowConfig * cfg,  // title, size, topBarHeight, dialModeDefault
                                            const tSynthLibCallbacks   * cbs);  // key/char/cursor/button/scroll/resize fn-ptrs
   Effort low, risk low, removes ~150 lines x2.

2. [PRIORITY] Popup lifecycle coordinator — the cleanest DECOUPLING win. SynthLib owns the popup
   WIDGETS (file/bank/alert browsers, context menu, menu bar) but NOT their orchestration, so each host
   re-implements it four separate times: (a) render order (every app calls render_context_menu ->
   render_file_browser -> render_bank_browser -> render_alert_dialog back-to-front, with the same
   "drawn last - modal" comment copy-pasted verbatim); (b) modal-priority CLICK dispatch cascade
   (if file_browser_active(){...return;} if bank_browser_active(){...} if alert_dialog_active(){...} —
   14 routing refs each in G2-Edit and SynthEdit mouseHandle.c); (c) the same cascade again for
   KEY/CHAR; (d) per-frame hover tick (update_context_menu_hover / update_menu_bar_hover /
   update_bank_browser_hover — the host must remember to call each every frame). That last one has
   ALREADY shipped real bugs: SynthEdit's own comments document "never actually called anywhere until
   now" hover reports (2026-07-11, 2026-07-24). An order-dependent contract spread across the host is
   fragile by construction. Fix = a coordinator façade that internalises the z-order (SynthLib
   registered the popups, so it knows the stacking):
       bool synthlib_popups_dispatch_click(tCoord coord, eClickPhase phase); // true if a modal consumed it
       bool synthlib_popups_dispatch_key(int key, int action);
       void synthlib_popups_tick(void);    // replaces all the update_*_hover() calls
       void synthlib_popups_render(void);  // one call, correct back-to-front order
   Each host's mouse_button / key / loop / render_frame collapses to a single guarded call. Turns a
   ~20-symbol order-sensitive surface into 4 functions. Effort medium, risk low-medium (mechanical but
   touches the hot input path in all three apps — sequence carefully). DO THIS FIRST of the priority set.

- SOUND ENGINE ACROSS CORES — investigated 2026-08-08, NOT BUILT, AND DEPRIORITISED THE SAME DAY:
  the single-core work listed at the bottom of this entry was enough to help materially, on the
  owner's ear at 15 voices. Threading is therefore not the next thing to reach for — take the rest of
  the single-core headroom first, and only come back here if the load figure says it is needed.
  KEPT IN FULL because the analysis is the expensive part and the API findings are checked rather
  than remembered.
  WHAT PROMPTED IT: one core saturated in Activity Monitor at 15 voices, with CoreAudio reporting
  "HALC_ProxyIOContext::IOWorkLoop: skipping cycle due to overload" — the audio callback missing its
  deadline, which is what the crackling was. The engine is single-threaded by design.
  THE THREADING IS NOT THE HARD PART. The render loop interleaves voices INSIDE the per-sample loop,
  so a barrier there would fire ~96000 times a second against a few microseconds of work each —
  hopeless. Threading requires restructuring first so that EACH VOICE RENDERS A WHOLE BUFFER, and
  synchronisation happens once per buffer (~200/s):
   * note events pre-resolved for the block on the audio thread, since voice ALLOCATION is global and
     has to stay serial — producing a per-voice event timeline the workers then honour;
   * per-voice scratch buffers for the signals that cross into the post-mix pass;
   * the post-mix pass (FX area + any shared-buffer module, see mark_post_mix_nodes) running over the
     summed block afterwards.
  DO THAT RESTRUCTURE ON ITS OWN FIRST. It is the prerequisite, it carries no real-time threading
  risk, and it should help SINGLE-CORE as well — one voice's state stays hot in cache instead of
  fifteen sets being cycled through on every sample.
  THE MACOS API PICTURE, checked against the SDK headers rather than remembered:
   * AudioToolbox's AudioWorkInterval.h sets out three cases. Ours is CASE 2 — an auxiliary realtime
     thread at the same cadence as the render request, expected to finish within it. Apple's
     instruction for that case is to implement a RENDER CONTEXT OBSERVER and join the worker threads
     to the workgroup the host passes it (kAudioUnitProperty_RenderContextObserver for AUv2,
     AUAudioUnit.renderContextObserver for AUv3).
   * AudioWorkIntervalCreate() is Apple's CASE 3 — threads at a cadence INDEPENDENT of the render
     cycle. It is the wrong tool here and is the one that gets reached for by mistake.
   * THE VST3 SDK HAS NO WORKGROUP INTERFACE AT ALL. `grep -rli workgroup` over pluginterfaces/ and
     public.sdk/ returns nothing, so there is no way for Ableton to hand a VST3 its workgroup. The
     fallbacks are (a) worker threads promoted with thread_policy_set THREAD_TIME_CONSTRAINT_POLICY,
     period matched to the buffer — what most VST3s do, but the OS does not know they belong to the
     host's deadline group, which matters on Apple Silicon where they can land on efficiency cores;
     or (b) SHIP AN AU AS WELL, where the sanctioned mechanism actually exists. The engine is already
     platform-free behind a hand-written wrapper, so a second thin wrapper is not a large lift.
   * The standalone is the easy case either way: CoreAudio exposes the device's own workgroup.
  WORTH KNOWING: hosts already parallelise across tracks and plug-ins, so a pool inside a plug-in can
  oversubscribe the cores the host was using and make the session worse. That is why several
  commercial plug-ins put their multicore behind a switch. Default it OFF in the VST3.
  ALREADY DONE ON ONE CORE (2026-08-08), in case that turns out to be enough:
   * OSC_DECIMATE_TAPS 128 -> 48. Measured worst image folding into 0..20 kHz: 128 taps -116 dB,
     64 -98 dB, 48 -90 dB, 32 -82 dB — and the PASSBAND DEVIATION IS 0.00 dB AT EVERY LENGTH, because
     the cutoff sits at 43 kHz. The taps buy stopband depth alone and 90 dB is below the noise floor
     of any playback path this will meet. This filter is the engine's largest single cost: it runs
     per oscillator per voice per oversampled sample.
   * The oscillator history array is float rather than double — that loop is bound by how fast it can
     be read, not by the arithmetic.
   * The per-tap integer modulo is gone from both decimators (bit-exact: same taps, same order).
   * pow(2.0, x) -> exp2() in the oscillator frequency and the filter cutoff, both per voice per
     oversampled sample.
   * The glide coefficient's exp() is hoisted out of the voice loop, and parameter smoothing runs
     once per sample rather than once per voice.
  MEASURE WITH THE STATUS LINE. It reads "N/M voices, load N%" — peak render time as a percentage of
  the buffer deadline, cleared on read, so it is always the worst buffer since you last looked.

- REVERB: MEASURED ON THE HARDWARE 2026-08-09. Read this before the 2026-08-08 notes below it, which
  are still accurate about what is left but were written when the room sizes were guesses.

  Method: a Pulse module's click through the Reverb, captured at 192 kHz with the dry click on a
  second output pair, both stereo outputs recorded. tools/capture.c + measure.py + analyse_ir.py; the
  captures are in ~/Documents/G2-Measurements/reverb/ (about 8 GB, not in the repo). Delay lengths come
  from the tail's AUTOCORRELATION, not from peak-picking: a delay tank's early response is only sparse
  for a few arrivals and dense after that, so a peak list changes with the threshold and is fiction. A
  recirculating length shows as a lag the whole tail correlates at.

  WHAT IS NOW MEASURED AND IMPLEMENTED:
   * THE FOUR ROOM SIZES, which the note below asked for. kReverbTypeScale is now
     {1.0, 1.2690, 1.5255, 1.6795}, referenced to SMALL rather than Large. Fitting one scale per room
     against every lag Small shows lands within 0.1% on four independent lengths — e.g. Small 4215 ->
     Large 6430 (predicted 6430.0) and -> Hall 7078 (predicted 7079.1). That also confirms the
     single-factor assumption itself, short diffusion lags included (Small 216 -> Large 329, exact).
     The old {0.5, 0.75, 1.0, 1.6} had Small at two thirds of its real size and Hall half again too big.
   * REVERB_COMB_MAX/REVERB_ALLPASS_MAX hardcoded x16/10 to match the old 1.6 maximum, so raising the
     scale to 1.6795 would have written 66 samples past the end of every comb. Now x18/10, with the two
     tied together in a comment. If you change the scale table, check that pair.

   * THE TIME DIAL IS LINEAR IN DECAY TIME, not cubic — implemented as kReverbDecayBase/Slope.
     Measured seconds = base + slope*value, value being the raw 0..127:

         room     Time 42   Time 85   Time 127    s per dial unit
         Small          -    1.95 s    2.89 s     0.02238
         Medium    2.01 s    3.72 s    5.49 s     0.04094
         Large     2.94 s    5.49 s    8.11 s     0.06082
         Hall      3.77 s    7.30 s   10.75 s     0.08212

     r2 0.996-0.998, slope consistent across both halves of the range to three digits. The old
     REVERB_TIME_CURVE cubic gave 17.58 s at Time 127 where Large measures 8.11 s, and its exponent was
     openly fitted by ear. Only Small rests on two points rather than three.
     THE SLOPE IS NOT PROPORTIONAL TO ROOM SIZE (Hall/Small 3.67 against a size ratio of 1.68), so Type
     sets the feedback GAIN as well as the lengths — hence a table rather than the size scale doing it.

   * BRIGHTNESS IS LOOP DAMPING — the structure was right, the amount was about twice too much. Now
     REVERB_BRIGHT_MAX/CURVE = 1.0/0.15, fitted against nine measured points of the dial and verified:
     the engine's low-band decay is 97-98% of the hardware's in ALL FOUR rooms, and the HF/LF decay-rate
     ratio is 0.53/0.70/1.00 against the hardware's 0.54/0.75/0.95 at Brightness 16/64/127.

     MEASURE THIS AGAINST THE RATIO OF PER-BAND DECAY RATES. Two other metrics actively mislead, and
     both of them fooled me first:
      - BROADBAND decay follows whichever band holds the energy. It made the engine look 40-60% short of
        its own target when its low band was within a second of the hardware. There was no shortfall.
      - ABSOLUTE tail colour at a fixed instant scores a linear dial BETTER than the correct curve,
        because colour at an instant mixes loop damping with everything outside the loop.
     Neither is a substitute for a rate.

     TWO WRONG DIAGNOSES ON THE WAY, recorded so they are not made again. It is NOT a feedback-gain
     error — the one-pole has unity DC gain, so fb sets the low-frequency decay exactly, and a render
     hits the requested time to 0.01 s with the filter out of the loop. And the damping is NOT a fixed
     loss outside the loop: the hardware's tail darkens as it decays, 14-16 dB over three seconds at mid
     dial against 1-3 dB at the top, which only something inside the loop does.

     STILL OPEN on brightness: the engine's tail is about 7 dB BRIGHTER in absolute terms than the
     hardware's at the top of the dial, even though their decay rates now agree. A loop that damps
     correctly but starts too bright means a fixed tilt somewhere outside the loop — one pass, not
     compounded, so it colours without touching decay. Not implemented; measured at roughly 7 dB.

     Hall at Time 127, tail measured 200 ms in, band energies relative to the whole:

         Bright   decay      100-500Hz   0.5-2k    2-6k   6-20k
              0   too damped to fit  -9.5    -24.6   -33.7   -30.9
             64   10.76 s            -9.8     -4.3    -3.6   -14.4
            127   11.83 s           -12.7     -5.7    -2.8    -9.8

     At 0 the tail is essentially gone above 500 Hz. Raising it lifts 6-20 kHz by about 5 dB and
     lengthens the decay by only ~10%, because broadband decay is dominated by the LF path.

  IT IMMEDIATELY FALSIFIED TWO OF MY OWN READINGS, which is what a known-truth reference is for:
   * ALLPASS LENGTHS DO NOT APPEAR IN A TAIL AUTOCORRELATION AT ALL. Rendering our own reverb — combs
     2232/2376/2554/2712, allpasses 194/298/450 — gives lags of 144, 158, 178, 322, 336, 480, the four
     comb lengths, and 2x two of them. Not one allpass length is present, at Time 0 or Time 127. A
     diffuser is flat in magnitude and smears phase without repeating, so it leaves no lag. Every one of
     those short lags is a DIFFERENCE between two comb lengths (2376-2232 = 144, 2712-2232 = 480). So the
     hardware's short lags constrain its set of lengths without being members of it.
   * "DROP THE LAGS THAT ARE SUMS OF OTHERS" IS NOT A VALID WAY TO FIND THE LENGTHS. A set closed under
     sums and differences explains itself both ways: Small has 6937 = 2338 + 4600 and also
     2338 = 6937 - 4600, so a filter labels one derived and keeps the other purely by iteration order,
     and produces two different confident answers for one dataset. Replaced by generating_sets(), which
     searches for the smallest set of lengths whose sums, differences and multiples explain every lag.
     Validated on the render: it recovers 2232/2376/2554/2712 exactly, in all four rooms.

  WHAT THE VALIDATED SEARCH SAYS ABOUT THE HARDWARE: not enough. Its power is in the ratio — 4 lengths
  explaining 12 lags predicts 8 of them; the smallest set explaining Small's 12 lags is EIGHT of them,
  which predicts 4 and proves little. The G2's tank has more lines than the lags above our noise floor
  can pin, which agrees with the ~31 lines noted below. THE NEXT STEP IS SIGNAL-TO-NOISE, not more
  analysis: the tail clears the floor by ~21 dB, and every extra 6 dB is four times the averaging or a
  quieter input path.

  A WARNING ABOUT DECAY MEASUREMENT, because it produced confident wrong answers twice: Schroeder
  backward integration assumes the segment ends in SILENCE. When it ends on a noise floor the integral
  is dominated by the noise's own energy falling off across the window, so an 8 s window reported ~15 s
  for every room and a 20 s window reported ~39 s for every Time setting from 42 up. Both are twice the
  window. analyse_ir.py now fits a line to the log envelope between a fixed drop below the peak and a
  margin above the measured floor, and prints the fitted span, r2 and extrapolation factor so a bad fit
  is visible. The G2's tail only clears our noise floor by about 21 dB, so every RT60 here is a x4
  extrapolation from a 14 dB fit — straight (r2 0.997), but say so.

- Mouse-up debounce while dragging — NOT BUILT, and probably not ours (2026-08-08). Owner reported
  drags occasionally ending on their own. DIAGNOSED AS HARDWARE, on the owner's own evidence: the
  same thing happens resizing windows and drag-selecting text in other applications, so it is a
  failing microswitch bouncing, not anything this code does. Recorded only because a debounce would
  help anyone else with an ageing mouse, and because the design has two traps worth writing down
  before someone reaches for the obvious version.
  IT CANNOT BE A DEBOUNCE IN THE USUAL SENSE — there is no way to know a re-press is coming except
  by waiting for it, so the only workable shape is DEFER THE RELEASE, never "release now and retract
  it if a press follows". Retracting would mean undoing a cable connect, a module shift-down and an
  undo push after the fact.
  SHAPE, if it is ever wanted:
   * Armed ONLY while a drag is active (module, cable, dial, rubber band). A global debounce would
     add latency to every click and interfere with double-click.
   * On up: stash the COORDINATE and the timestamp, FREEZE the drag, do not end it.
   * On down inside the window: discard the pending release, unfreeze, the drag simply continues.
   * On a tick past the window: run the real release using the STASHED coordinate. This matters —
     the cable connect hit-tests the release position, so firing it at wherever the pointer has
     since drifted would connect the wrong thing.
   * Freeze rather than keep following the pointer, or every legitimate release visibly overshoots
     and snaps back.
   * 40-60 ms: above contact bounce, below a deliberate human re-click.
   * The standalone blocks in glfwWaitEvents() when idle, so a pending release needs a timeout tick
     or a drag released with no further input hangs until the next event. Slots into the existing
     ladder at graphics.c:2614, which already does this for the button auto-repeat. The plug-in has
     ensureTickTimer.
  MEASURE BEFORE BUILDING. Log the interval between a mouse-up during a drag and the next
  mouse-down: switch bounce is sub-20 ms, unmistakably. If the gaps are 200 ms+ it is NOT bounce and
  a debounce would mask a software fault rather than fix it — look instead at the cursor warp in
  start_cursor_drag() (dial drags hide and warp the pointer) and, in the plug-in, the view's
  tracking area.


DO NOT RE-TRY (conclusions from completed work — the reasoning is gone from this file, the constraint is not)

- FT_LOAD_FORCE_AUTOHINT in the glyph rasteriser: tried and REJECTED. Crisper, but it changes glyph
  advances, and with canonical-advance positioning it renders "R andomA 1" / "554.4H z". Do not re-try
  without also making get_text_width() use the same hinted advances — which it cannot, as it never sees

  while leaving horizontal metrics linear.
- Text layout is deliberately NOT driven by the per-size atlases. get_text_width() and everything built
  on it stay on ONE canonical metrics set (gCanonInfo, measured once at GLYPH_REFERENCE_PX) so widths
  stay continuous and boxes fit. The pen advances by the canonical advance; only each glyph's final
  position is rounded. That costs sub-pixel letter spacing and buys pixel alignment — the right trade
  at 6px.

  ascent (round(coord.y + gMaxAscent * scaleFactor), rounded ONCE). An earlier version used each
  atlas's OWN rounded ascent, which rounds a second time against a rasterization whose em height only
  approximates the requested one — that is what caused the intermittent "text renders slightly low"

- The reverse-queue design deliberately keeps coalescing dirty-bits as flags, not messages
  (gotPatchChangeIndication[], gotPerfSettingsChangeIndication, gReDraw, EmuUtility's gNeedLcdFull/

  reverse queue would be speculative.
- gLcd uses a mutex, not a double-buffer, because deltas mutate the accumulated frame in place so there
  is no clean front/back to swap. The lock is never held over a GL call.
- eMsgCmdScanDevices is COALESCED in EmuUtility's drain (a local bool; the scan runs once after the
  batch) because a rescan is a wanted-state, not an event: one hub plug can fire several
  kMIDIMsgSetupChanged notifications and each scan walks every destination at 15ms stagger.
- module->connector[i].type deliberately stores only the raw base type, never the upRate promotion —
  protocol.c's own upRate-propagation walk depends on it being the permanent declared type. Use
  effective_connector_type(baseType, upRate) at the point of use instead.
- menus.c is NOT a commonalise candidate. The underlying mechanism (tMenuItem, open_context_menu,
  contextMenu.c) is already fully shared via SynthLib. G2-Edit's menus.c is still 2125 lines
  (EmuUtility/SynthEdit's are 26/95), but what remains is legitimately G2-specific domain action logic
  operating on tModule/tParam/tCable, which do not exist in the other two apps.
